We're building Boopada, a trip planner. Here's the roadmap so you have the
whole picture. We'll go roughly in this order, one piece per session:

1. Traveller profile (today).
2. Bucket list: places and experiences to save for later.
3. Trips: create a trip from legs of cities and nights, with a draft day-by-day
   plan.
4. Itinerary editing: add, move and remove activities and days.
5. Itinerary view: the trip laid out day by day, with daily and trip totals.
6. Location to-dos: to-dos per day, surfaced when you arrive somewhere.
7. Activity suggestions and local transport costs.
8. Curation advisor: tells you what could be better and can fix it for you.
9. Chat: a command box on the trip page. It understands exactly these commands:
   - "add <activity name> to day <n>"
   - "remove <activity name> from day <n>"
   - "undo"
   - "make day <n> lighter": apply the advisor's lighten suggestion for that
     day, or remove that day's longest activity if there isn't one
   - "interest add <category>" / "interest remove <category>"
   - "what can be better": list the advisor's suggestions
   POST /api/chat { trip_id, message } returns
   { reply, changed, suggestions? }. Anything else gets a reply listing the
   commands, with changed: false.

Today: the traveller profile.

- GET /api/profile and PUT /api/profile with: home_currency, home_airport,
  cabin_class (economy | premium_economy | business | first),
  daily_activity_budget (optional), interests.
- Before anything is saved, GET returns home_currency USD, home_airport SFO,
  cabin_class economy, no budget, no interests.
- Validate: currency and airport must be ones the providers know.
- A /profile page to view and edit it (data-testid: profile-form,
  profile-save).

Two decisions to keep for the whole project:
- Money, everywhere in the API, going in and coming out, is
  { "amount_minor": integer, "currency": "ISO code" } in the currency's minor
  units: JPY and VND have none, JOD has three. No decimal strings, no floats.
  Our prototype used decimal strings and totals drifted.
- Interests are not free text. They're the providers' activity categories:
  culture, food, nature, adventure, nightlife, wellness, tour. Reject anything
  else.

Conventions for this project:
- Monorepo, bun. The app is apps/web (Next.js). Data providers come from
  @workspace/providers; use its fixture bundle.
- Storage: SQLite at the path in BOOPADA_DB_PATH (default ./data/boopada.sqlite).
  Create or upgrade the schema automatically on startup.
- Time: the current time is BOOPADA_NOW (ISO timestamp) when set, otherwise the
  system clock.
- API: JSON under /api. Errors return 4xx with { "error": { "code", "message" } }.
- One traveller, no login.
- The app must run with `bun run build`, then `bun run start` in apps/web
  (port from PORT).
- Before you finish, `bun run lint`, `bun run typecheck` and `bun run test` pass.

Next: the bucket list.

- POST /api/bucket { title, city_id?, notes?, estimated_daily_spend? } returns
  the item with an id and created_at. GET /api/bucket returns { items }.
  PATCH /api/bucket/{id} edits. DELETE /api/bucket/{id} deletes.
- Unknown city_id is a 400.
- A /bucket page listing items, with add and delete (data-testid: bucket-item-{id},
  bucket-add, bucket-delete-{id}).

A decision for the whole app, not just this feature: we never hard-delete

soft delete, and POST /api/undo restores the most recent deletion (409 with
code "nothing_to_undo" when there's nothing). Deleted things never show up in
any list, total or suggestion.
