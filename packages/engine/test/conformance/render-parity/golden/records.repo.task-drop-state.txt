== shard decisions/D1.md (1799 bytes) ==
<!-- generated by sofar — do not hand-edit; truth lives in events.jsonl -->

D1 — 2026-08-05
chose: Exactly ONE new terminal status named `dropped`, added to both TASK_STATUSES and PHASE_STATUSES. It requires a reason note, and progress renders it as a visible third term — `9 done, 1 dropped, 0 remaining` — only when drops exist, leaving `9/10 tasks done (90%)` untouched otherwise.
over: (a) Adding two or three states (skipped / abandoned / no-longer-needed) — `blocked` already covers "wants to happen, can't yet" and should keep nagging; only the terminal "decided not to happen" is missing, and near-synonyms are a choice an agent gets wrong at 2am. (b) Counting drops as done (10/10) — inflates the numerator and lies about what was built. (c) Silently subtracting drops from the denominator (9/9, 100%) — dropping the hard half of an initiative would quietly read as complete; scope would vanish untraceably. (d) Expressing drops without a new state: deleting the task loses the history of having considered it, and marking it done is dishonest.
because: `blocked` is doing two incompatible jobs, and the render is wrong info: repo-memory-capture 4.1 is a deliberate scope call that shows as `[pending] 0/1` with progress frozen at 90%. Splitting off a terminal outcome fixes the signal while keeping the vocabulary small enough to use without thinking. The three-term render is the honest middle: `done` keeps meaning delivered, the denominator never shrinks silently, and "0 remaining" is the completion signal — with the extra term staying quiet in the common case, which the injected digest's token budget cares about. Name: `skipped` reads temporary and invites revisiting; `abandoned` makes a deliberate call sound like neglect; `dropped` is what people actually say.

== shard decisions/D2.md (1620 bytes) ==

D2 — 2026-08-05
chose: `dropped` ships as a real TASK_STATUSES/PHASE_STATUSES enum member, accepting that published 0.17.2 skips such events. Paired with a mandatory companion fix: fold must tolerate an unknown TASK STATUS inside plan_updated by keeping the rest of the plan (warn + coerce that one task) instead of rejecting the whole event.
over: Encoding the drop as a sidecar field (`status:"blocked", dropped:true`), which was verified to degrade perfectly on 0.17.2 — old engines render today's exact semantics with no warnings and no plan loss, because payload validation is permissive about unknown extra fields.
because: The sidecar buys a clean degrade with a permanent lie: the raw log would say `blocked` for a task that is dropped, and this record's whole value is that it does not flatter or misstate. Two fields encoding one concept must then be threaded through every consumer forever, and the NEXT enum addition faces the identical choice under the identical pressure. The enum's cost is bounded instead: no data is ever lost (the log stays intact — only a stale reader's render is wrong), it self-heals the moment the reader upgrades, and repo memory already carries the rule that the global install must be upgraded after each publish. The plan_updated cliff found in 1.1 is the only genuinely harmful part, and it is a GENERAL forward-compatibility defect rather than anything specific to `dropped` — fixing it once at the fold boundary retires that whole class, which the sidecar hack would merely route around.

== shard decisions/D3.md (1378 bytes) ==

D3 — 2026-08-05
chose: A drop must carry a reason, enforced by REJECTING the tool call (`sofar_update_task` fails validation when status is `dropped` and note is empty), with doctor additionally warning when a drop's reason cites no decision. State keeps `drop_notes` so the reason stays addressable after the fold.
over: Warning instead of rejecting, and requiring nothing at all (matching how `blocked` currently works, where the note is optional).
because: `dropped` is the one status that closes a task without delivering it, so the stated reason IS the entire record that a decision was made rather than that the work was quietly forgotten — and unlike a wrong `pending`, nothing downstream will ever nag anyone into supplying it later, because a drop is terminal and stops appearing in remaining work. Rejecting is safe here: the worst case is that an agent leaves the task `pending` or `blocked`, which is exactly today's status quo rather than a regression, and the error message names what to supply. The cite-check is a warning rather than a rejection because a reason may legitimately predate its decision, or be self-contained — but a drop whose "why" points nowhere loses its justification the moment the author's context ends, which is the failure this record exists to prevent.
