Date: 2026-09-15. Audit only. Recommendations below are not adopted decisions or implementation changes.

## Verdict
Keep the initiative. It targets real friction and follows established context/harness engineering practice, but its present plan does not establish industry leadership. The strongest opportunity is to combine low bookkeeping, precise decision history, cross-agent continuity, and completion backed by independent, replayable evidence. Leadership must be measured against direct memory/harness competitors as well as native agent memory.

Scope: all 18 r1-fixes tasks; bench-refresh goal, decisions and frozen round-1 pre-registration; self-improve dependencies; targeted engine/schema/SPEC reads; primary-source research. Main baseline was 8b4c33c. The separate implementation worktree had task 1.1 committed as 7f097a9 and task 1.2 active. Main's 0/18 projection was behind that worktree. I independently ran first-session-notice.test.ts in the implementation worktree: 8/8 passed. That validates the targeted behavior, not the predicted token savings. No implementation, plan, task status, benchmark, install or release changes made by this audit. The unfinished 1.2 patch was not certified.

## Highest-priority findings

### A1 — Verification needs a persisted acceptance contract (task 3.1)
Today driver/drive.ts computes handoffReason after folding the record, with no independent acceptance check. queuedTasks only includes active/pending tasks; handoffReason can observe any newly resolved task, including dropped tasks, rather than exclusively the assigned task. A newly added check that merely prints failure would leave an agent-marked done task outside the next queue and could skip it on restart.

Specify task acceptance independently from the agent's completion claim. Evidence should identify task, attempt, command/arguments, working directory, checked code state (including relevant uncommitted changes), validator definition/version, result, timeout and diagnostics. A pass must become invalid when the checked inputs change. Persist the verification result through packages/schema and derive queue eligibility from it. Define task-policy versus threshold-policy multi-task behavior, failed-check retries, crash during verification, interrupted runs, missing checks and deliberately dropped tasks. Never equate dropped with acceptance-tested success.

Use operator-approved commands; do not accidentally execute them under broader permissions than the launched agent. A local acceptance check is not the hidden benchmark evaluator. Protected evaluation belongs outside the agent's writable checkout; a checksum detects a changed evaluator but does not by itself prevent the agent reading it.

Proof: false completion, a failing check followed by restart, successful check followed by code changes, sibling task completion, missing binary, timeout, killed validator, and multiple tasks under threshold policy.

### A2 — Automatic capture overlaps another initiative and contradicts commit policy (2.5, 2.6, self-improve 1.2)
docs/SPEC.md, Commit attribution, explicitly derives commit evidence from Git and never records commit events. Its Hooks contract exempts git/sofar commands to keep the tree settleable. Task 2.5's literal proposal to record commits can reintroduce the cycle where committing the record immediately dirties it again. Keep Git attribution derived unless an explicit Decision replaces that contract. A task-id prefix alone is ambiguous across initiatives; retain initiative identity and existing trailers.

Files and shell commands already have mechanical capture. What is missing is normalized outcome evidence, not a new parallel capture system. self-improve 1.2 separately owns exit codes, is_error and failure hooks. Assign one schema/implementation owner and make the other initiative consume it.

Capture observed outcomes, not guessed success. A successful shell invocation is not necessarily a passing test suite; shell composition, background processes and command wrappers complicate attribution. Use structured runner output where available, and represent unavailable outcomes as unknown. Redact and bound errors BEFORE the append-only record. Keep optional unsynced local statistics separate from durable record truth; gitignored is not equivalent to excluded from sofar sync.

Publish a per-host capability matrix and truthful fallbacks. Claude and Cursor hooks differ; the existing CLI-only protocol explicitly says some hosts lack write-back enforcement. Do not market universal automatic capture until each claimed host passes conformance fixtures.

### A3 — Decision expiry can silently erase rules or break replay (3.2)
The SPEC requires stable injection for unchanged records and standing rules that do not age out. If renderStatus evaluates valid_until against wall-clock time, identical events render differently tomorrow. If counters decay standing rules, an important rarely-used rule can disappear.

Use immutable event identities for references, explicit supersession links, retained history, and separate statuses for active, superseded, expired and conflicted material. An authorized explicit transition can change a standing rule; low retrieval frequency cannot. If time-based validity is desired, define a recorded evaluation boundary or a new expiry event so replay remains explainable. A different live-clock contract requires an explicit SPEC decision first. Concurrent incompatible replacements should surface conflict rather than silently choose a winner.

ACE and temporal graphs are useful prior art, but neither establishes that raw frequency counters measure a decision's correctness.

### A4 — Publication currently precedes the evidence gate (4.2–4.3)
The plan puts owner npm publication in 4.2 before handing the release to round 2 in 4.3, while the goal requires D19 evidence before shipping. Distinguish an immutable release candidate used in the benchmark from a stable release promoted after the gate. Proposed sequence: acceptance suite -> frozen candidate -> chain-A validation/ablations -> sealed chain-B and addendum evaluation -> verdict -> owner publication.

D19 needs an executable comparison rule. Orient lower-is-better metrics correctly; track both absolute performance and margins, because holding a negative margin still means losing. Report win, loss, parity and inconclusive, with uncertainty. Three repeated chains are an initial signal, not assurance that a five-point gain is real; tests within a chain are correlated. Any reinterpretation of D19's exact no-shrinking rule requires a new owner decision, not an audit silently weakening it.

The current round-1 pre-registration already correctly reports all three repetitions, avoids p-values, separates costs by agent and forbids public tuning-set claims. Preserve it unchanged. C6/C7/C8 are deferred addenda, so an all-eight-claims gate needs those evaluations or must explicitly report them unmeasured.

### A5 — The comparison set misses direct competitors
The frozen round-1 matrix is useful for native-memory comparisons, but cannot support an industry-wide lead claim. Add appropriately scoped round-2 or subsequent pre-registered comparisons against Beads and PROJECTMEM; consider OpenMemory as a memory-layer arm and Letta Code as a separate full-harness comparison. Use standard recommended setups and disclose extra inference/infrastructure. Keep model and effort fixed within a memory comparison; compare full harnesses separately when equivalence is impossible.

Native memories, git history and shared profiles need fresh isolation per independent chain. Re-pin competitors at round boundaries, never mid-round. Also re-run the previous sofar release against the same new competitor snapshot: otherwise a changed model or competitor version is confounded with the effect of r1-fixes.

### A6 — Smaller context is a constrained optimization (2.1–2.4, 3.3)
A 6k-character target is a hypothesis, not a universally correct context budget. Protect exact relevant standing constraints, current task, blockers, unresolved verification failures, decision identity and next action. Deduplicate using IDs/fields, not approximate semantic similarity that can erase different scope or negation. Overflow should point to exact retrievable evidence. Assess total episode cost, including extra fetches, tool discovery and rework.

The current update_task constraint echo deliberately resurfaces rules at the moment work begins. Removing it needs an alternative point-of-use signal and an ablation; it is not necessarily pure duplication. Similarly, CLI-first review/close/find can trade schema bytes for shell/discovery calls.

Stable prefixes are sound practice, but sofar does not control the whole host prompt, provider cache key, TTL or model routing. Measure actual cached/uncached input, output, latency and total cost within the same host. Moving reminders later can help stability, but must still work when drive has no new user prompts. Char count is a transport constraint, not a token/cost metric.

- Manus recommends stable prompt prefixes and preserving retrievable detail. Useful principles, dependent on actual cache behavior of the host. [Context engineering](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).

- Graphiti combines temporal validity, semantic retrieval, keyword search and graph traversal. BM25 is one component, not sufficient evidence of state-of-the-art retrieval. Sofar can test scoped lexical plus existing graph signals without adding model calls. [Graphiti](https://github.com/getzep/graphiti).
- Beads documents structured persistent memory, dependency-aware task readiness and atomic claiming. It is a close workflow comparator. [Beads](https://github.com/gastownhall/beads).
- PROJECTMEM describes append-only typed events, deterministic projections, offline operation and pre-action warnings against failed approaches. That directly defeats a broad uniqueness claim for local event-sourced memory with deterministic guards. Its paper reports a small self-study, not controlled superiority; benchmark it instead of accepting its marketing claims. [Paper](https://arxiv.org/abs/2606.12329), [repository](https://github.com/riponcm/projectmem).
- Letta's context repositories already combine Git-versioned memory and progressive disclosure. Git-backed portable memory alone is not unique. [Context repositories](https://www.letta.com/blog/context-repositories/).
- OpenMemory targets persistent context across MCP-compatible coding agents. Cross-tool memory is already a competitive category. [OpenMemory](https://mem0.ai/openmemory).
- Current Claude hooks documentation includes parallel hook execution, failure hooks and PostToolBatch. A capability-probed batch hook could coalesce context injection while retaining per-tool evidence; do not assume the pinned benchmark host implements every current documented hook. [Claude hooks](https://code.claude.com/docs/en/hooks). Cursor has its own input/lifecycle contracts requiring separate tests. [Cursor hooks](https://cursor.com/docs/hooks).
- Agent evaluations need repeated trials and isolated environments; apparent successes and consistent reliability answer different questions. [Anthropic evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

## Highest-priority findings

### A1 — Verification needs a persisted acceptance contract (task 3.1)
Today driver/drive.ts computes handoffReason after folding the record, with no independent acceptance check. queuedTasks only includes active/pending tasks; handoffReason can observe any newly resolved task, including dropped tasks, rather than exclusively the assigned task. A newly added check that merely prints failure would leave an agent-marked done task outside the next queue and could skip it on restart.

Specify task acceptance independently from the agent's completion claim. Evidence should identify task, attempt, command/arguments, working directory, checked code state (including relevant uncommitted changes), validator definition/version, result, timeout and diagnostics. A pass must become invalid when the checked inputs change. Persist the verification result through packages/schema and derive queue eligibility from it. Define task-policy versus threshold-policy multi-task behavior, failed-check retries, crash during verification, interrupted runs, missing checks and deliberately dropped tasks. Never equate dropped with acceptance-tested success.

Use operator-approved commands; do not accidentally execute them under broader permissions than the launched agent. A local acceptance check is not the hidden benchmark evaluator. Protected evaluation belongs outside the agent's writable checkout; a checksum detects a changed evaluator but does not by itself prevent the agent reading it.

Proof: false completion, a failing check followed by restart, successful check followed by code changes, sibling task completion, missing binary, timeout, killed validator, and multiple tasks under threshold policy.

### A2 — Automatic capture overlaps another initiative and contradicts commit policy (2.5, 2.6, self-improve 1.2)
docs/SPEC.md, Commit attribution, explicitly derives commit evidence from Git and never records commit events. Its Hooks contract exempts git/sofar commands to keep the tree settleable. Task 2.5's literal proposal to record commits can reintroduce the cycle where committing the record immediately dirties it again. Keep Git attribution derived unless an explicit Decision replaces that contract. A task-id prefix alone is ambiguous across initiatives; retain initiative identity and existing trailers.

Files and shell commands already have mechanical capture. What is missing is normalized outcome evidence, not a new parallel capture system. self-improve 1.2 separately owns exit codes, is_error and failure hooks. Assign one schema/implementation owner and make the other initiative consume it.

Capture observed outcomes, not guessed success. A successful shell invocation is not necessarily a passing test suite; shell composition, background processes and command wrappers complicate attribution. Use structured runner output where available, and represent unavailable outcomes as unknown. Redact and bound errors BEFORE the append-only record. Keep optional unsynced local statistics separate from durable record truth; gitignored is not equivalent to excluded from sofar sync.

Publish a per-host capability matrix and truthful fallbacks. Claude and Cursor hooks differ; the existing CLI-only protocol explicitly says some hosts lack write-back enforcement. Do not market universal automatic capture until each claimed host passes conformance fixtures.

### A3 — Decision expiry can silently erase rules or break replay (3.2)
The SPEC requires stable injection for unchanged records and standing rules that do not age out. If renderStatus evaluates valid_until against wall-clock time, identical events render differently tomorrow. If counters decay standing rules, an important rarely-used rule can disappear.

Use immutable event identities for references, explicit supersession links, retained history, and separate statuses for active, superseded, expired and conflicted material. An authorized explicit transition can change a standing rule; low retrieval frequency cannot. If time-based validity is desired, define a recorded evaluation boundary or a new expiry event so replay remains explainable. A different live-clock contract requires an explicit SPEC decision first. Concurrent incompatible replacements should surface conflict rather than silently choose a winner.

ACE and temporal graphs are useful prior art, but neither establishes that raw frequency counters measure a decision's correctness.

### A4 — Publication currently precedes the evidence gate (4.2–4.3)
The plan puts owner npm publication in 4.2 before handing the release to round 2 in 4.3, while the goal requires D19 evidence before shipping. Distinguish an immutable release candidate used in the benchmark from a stable release promoted after the gate. Proposed sequence: acceptance suite -> frozen candidate -> chain-A validation/ablations -> sealed chain-B and addendum evaluation -> verdict -> owner publication.

D19 needs an executable comparison rule. Orient lower-is-better metrics correctly; track both absolute performance and margins, because holding a negative margin still means losing. Report win, loss, parity and inconclusive, with uncertainty. Three repeated chains are an initial signal, not assurance that a five-point gain is real; tests within a chain are correlated. Any reinterpretation of D19's exact no-shrinking rule requires a new owner decision, not an audit silently weakening it.

The current round-1 pre-registration already correctly reports all three repetitions, avoids p-values, separates costs by agent and forbids public tuning-set claims. Preserve it unchanged. C6/C7/C8 are deferred addenda, so an all-eight-claims gate needs those evaluations or must explicitly report them unmeasured.

### A5 — The comparison set misses direct competitors
The frozen round-1 matrix is useful for native-memory comparisons, but cannot support an industry-wide lead claim. Add appropriately scoped round-2 or subsequent pre-registered comparisons against Beads and PROJECTMEM; consider OpenMemory as a memory-layer arm and Letta Code as a separate full-harness comparison. Use standard recommended setups and disclose extra inference/infrastructure. Keep model and effort fixed within a memory comparison; compare full harnesses separately when equivalence is impossible.

Native memories, git history and shared profiles need fresh isolation per independent chain. Re-pin competitors at round boundaries, never mid-round. Also re-run the previous sofar release against the same new competitor snapshot: otherwise a changed model or competitor version is confounded with the effect of r1-fixes.

### A6 — Smaller context is a constrained optimization (2.1–2.4, 3.3)
A 6k-character target is a hypothesis, not a universally correct context budget. Protect exact relevant standing constraints, current task, blockers, unresolved verification failures, decision identity and next action. Deduplicate using IDs/fields, not approximate semantic similarity that can erase different scope or negation. Overflow should point to exact retrievable evidence. Assess total episode cost, including extra fetches, tool discovery and rework.

The current update_task constraint echo deliberately resurfaces rules at the moment work begins. Removing it needs an alternative point-of-use signal and an ablation; it is not necessarily pure duplication. Similarly, CLI-first review/close/find can trade schema bytes for shell/discovery calls.

Stable prefixes are sound practice, but sofar does not control the whole host prompt, provider cache key, TTL or model routing. Measure actual cached/uncached input, output, latency and total cost within the same host. Moving reminders later can help stability, but must still work when drive has no new user prompts. Char count is a transport constraint, not a token/cost metric.

## Research: established practice and where sofar can differentiate
Sources checked 2026-09-15. These are primary descriptions of capabilities/research, not independent proof that any tool beats sofar.

- Claude Code already uses a compact auto-memory index with topic files. This supports index-first context but makes it baseline practice. [Memory documentation](https://code.claude.com/docs/en/memory).
- Anthropic's long-running harness work emphasizes incremental tasks, clear handoff artifacts and end-to-end verification. This supports 3.1; it does not establish sofar's predicted gain. [Harness research](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents).
- LangChain reports 52.8% -> 66.5% on Terminal-Bench 2.0 with a fixed model after a collection of harness changes. The 13.7-point gain is real as their reported result; it is not an isolated causal estimate for adding a verification command. [Harness engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering).
- Manus recommends stable prompt prefixes and preserving retrievable detail. Useful principles, dependent on actual cache behavior of the host. [Context engineering](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).
- ACE uses structured evolving playbooks to avoid loss from repeated summarization. Borrow stable items and incremental changes; its model-based adaptation results do not establish performance for a deterministic counter-only system. [ACE paper](https://arxiv.org/abs/2510.04618).
- Graphiti combines temporal validity, semantic retrieval, keyword search and graph traversal. BM25 is one component, not sufficient evidence of state-of-the-art retrieval. Sofar can test scoped lexical plus existing graph signals without adding model calls. [Graphiti](https://github.com/getzep/graphiti).
- Beads documents structured persistent memory, dependency-aware task readiness and atomic claiming. It is a close workflow comparator. [Beads](https://github.com/gastownhall/beads).
- PROJECTMEM describes append-only typed events, deterministic projections, offline operation and pre-action warnings against failed approaches. That directly defeats a broad uniqueness claim for local event-sourced memory with deterministic guards. Its paper reports a small self-study, not controlled superiority; benchmark it instead of accepting its marketing claims. [Paper](https://arxiv.org/abs/2606.12329), [repository](https://github.com/riponcm/projectmem).
- Letta's context repositories already combine Git-versioned memory and progressive disclosure. Git-backed portable memory alone is not unique. [Context repositories](https://www.letta.com/blog/context-repositories/).
- OpenMemory targets persistent context across MCP-compatible coding agents. Cross-tool memory is already a competitive category. [OpenMemory](https://mem0.ai/openmemory).
- Current Claude hooks documentation includes parallel hook execution, failure hooks and PostToolBatch. A capability-probed batch hook could coalesce context injection while retaining per-tool evidence; do not assume the pinned benchmark host implements every current documented hook. [Claude hooks](https://code.claude.com/docs/en/hooks). Cursor has its own input/lifecycle contracts requiring separate tests. [Cursor hooks](https://cursor.com/docs/hooks).
- Agent evaluations need repeated trials and isolated environments; apparent successes and consistent reliability answer different questions. [Anthropic evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

## Measurement and competitive proof
Keep the existing numerical predictions but label them unvalidated. Do not add the -40% capture savings, -3 to -5 turns and schema/digest savings: they overlap. Use staged ablations on the tuning workload to attribute effects, and test the final combined candidate once on sealed held-out work.

For bookkeeping, freeze the numerator and denominator before testing. Report absolute memory-related calls/tokens, total task cost, and overhead fraction. A ratio can improve simply because useful work became more expensive. The pre-registration's M6 marks turns touching memory; mixed-purpose turns need a documented attribution convention. Preserve cached/uncached/output categories and quality-normalized completed work. Do not convert a raw token saving into an exact subscription-capacity guarantee.

One travel-app chain supports claims on that workload. Before claiming broad industry lead, include independent workload families and short maintenance episodes, plus cross-agent handoffs and conflicting concurrent work. Preserve the round-1 freeze. Sequential paired runs, environment isolation, per-chain variance, declared failure handling and future unseen holdouts matter more than increasing the count of correlated assertions.

Suggested prioritization:
1. Finish wave-1 correctness/usability fixes and specify compatibility.
2. Define the shared outcome schema, decision lifecycle and durable acceptance contract.
3. Implement verified completion and quick-work capture using those foundations.
4. Tune digest/routing/retrieval with measured ablations; trim tool schemas when total episode cost supports it.
5. Freeze the candidate, run current direct competitors and required held-out addenda, then promote a stable release only after the recorded verdict.

Do not add a language rewrite to this initiative without profiling evidence. The present loss study points first to avoidable model turns and protocol friction. Native performance work can be separately justified by measured hook/fold latency.

Make sofar the most dependable way to continue verified work across coding agents, with low overhead even for tiny fixes and an inspectable explanation of why each decision or reminder exists. That is a testable product advantage. Novelty and competitor superiority remain unproven until the stronger comparisons run.
