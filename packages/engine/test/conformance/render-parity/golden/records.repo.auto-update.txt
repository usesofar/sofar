== shard decisions/D1.md (2005 bytes) ==
<!-- generated by sofar — do not hand-edit; truth lives in events.jsonl -->

D1 — 2026-08-05
chose: D1: Auto-update means a cached version check that only ever TELLS you. A detached child refreshes ~/.local/state/sofar/update.json (24h TTL, XDG_STATE_HOME honored); every foreground surface only READS that file, so no command ever waits on the network. The parent claims the slot (writes checked_at before spawning) so the statusline, which renders every prompt, cannot start a thundering herd. Surfaced on the statusline (cyan info segment, color law) and on status/init/doctor as a trailing line. Checks run ONLY when planUpgrade() resolves global-npm, and never under CI or SOFAR_NO_UPDATE_CHECK. True auto-install exists but is opt-in (`sofar upgrade --auto on`, ~/.config/sofar/config.json) and is pitched only in runUpgrade's success message, at the moment the chore was just felt.
over: Installing updates silently by default; a synchronous `npm view` on the statusline or SessionStart hot path; a new doctor AXIS, which would turn doctor's exit code non-zero merely because a release landed; nagging source checkouts, local deps and npx runs, which either cannot self-upgrade or are already latest; and printing the --auto pitch before --auto exists.
because: `sofar upgrade` already solves installing correctly (it derives the real npm prefix from the running binary). What it cannot do is tell you an update exists — that is the whole gap. Notification is safe; unattended installation is not symmetric with it, because upgrading replaces the binary AND leaves repo wiring stale (runUpgrade's own success message says to re-run `sofar init` for hook shims and the protocol block), so the install must stay a thing the user chose. The read/refresh split is what makes the hint free: reading a JSON file is sub-millisecond, and the statusline path renders on every prompt. Gating on global-npm kills dev-noise in this very repo, where a source checkout would otherwise nag on every render.

M1 — 2026-08-05
The CLI ships as THREE bundles (build.mjs): dist/cli.js is the boot entry, dist/fast.js is the hot path (boot routes only `event` and `statusline` there, speed-2 T1), dist/full.js is everything else. Two consequences that bite: (a) any code that re-launches sofar from inside sofar must spawn dist/cli.js — spawning `fileURLToPath(import.meta.url)` from a module bundled into fast.js runs a file with no top-level entry, which exits silently; (b) a feature added to a statusline code path lands in the fast bundle, so check `stat -f%z packages/engine/dist/fast.js` before and after. esbuild does tree-shake unused exports across the cli/ modules, so importing a heavy module for one pure helper is usually free — verify by grepping dist/fast.js for a string unique to the code you expect to be absent.

M3 — 2026-08-05
Run `sofar new <slug>` BEFORE `sofar_start_session`, never after. start_session pins the session to whatever initiative resolves at that moment, and `sofar new`'s rebinding of the branch does NOT retroactively move it — every decision, task update, memory and hook event for the rest of the session files under the OLD initiative while bindings.json innocently reads the new one. Calling sofar_start_session again with an explicit `initiative` does not fix it either: the PostToolUse hook keeps resolving through the session registry and goes on writing to the old record. Recovery that works: extract the added lines from the wrong log with `git diff -U0 <log> | grep '^+{'`, rewrite the `"initiative"` field to the right slug, `sofar import` that NDJSON (it appends and regenerates every projection), then `git restore` the wrong initiative's directory. The MCP tools' explicit `initiative` argument does route correctly, so use it for any write after the mistake is spotted.
