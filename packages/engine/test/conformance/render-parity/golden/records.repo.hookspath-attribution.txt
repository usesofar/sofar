D1·vy9k — 2026-08-13
rule: Ask git where hooks actually live (effectiveHooksDir) — never assume `<common>/hooks`, and never write into a hooks directory that is tracked in the user's repo.
chose: Resolve `core.hooksPath` and compare it against `<common>/hooks` by realpath: when it names that same directory — absolutely or relatively — install normally; when it names another, keep skipping but print that directory's `prepare-commit-msg` and the exact line to add. One resolver, core/attribution.ts effectiveHooksDir, used by both `sofar init` and doctor.
over: Treating any `core.hooksPath` as a skip (the 0.26.0 behaviour), and the opposite extreme of installing into whatever directory it names — including a husky or lefthook directory, which is tracked in the repo, so sofar would be adding a COMMITTED file to the user's project rather than an untracked one under .git.
because: Setting core.hooksPath to `.git/hooks` explicitly is common and harmless, and refusing it installs nothing for no reason while telling the user `.git/hooks` is inert when it is the live hooks dir — found in the field on 0.26.0 in brillo, where the value was the repo's own `.git/hooks`. The resolution has to come from `git config --get`, never from parsing `.git/config`, because the value can arrive from the global or system scope or through an include; that spawn is why the helper lives in core/attribution.ts rather than core/git.ts, whose no-subprocess guarantee the hook shims depend on. doctor shares it because the same wrong question there reports attribution off for a working hand-installed husky hook.
guard: path:packages/engine/src/cli/init.ts,packages/engine/src/cli/doctor.ts,packages/engine/src/core/attribution.ts

M1 — 2026-08-13
VERIFYING A PACKED BUILD: put the tarball's bin FIRST on PATH, or you are testing the installed engine and not the artifact. The prepare-commit-msg shim resolves `sofar` from PATH by design (D5: no absolute path, so it survives any install layout), so `npm install -g --prefix <tmp> sofar.sh-<v>.tgz` and then invoking the CLI by its full path proves nothing about attribution — the hook still shells out to whatever `sofar` PATH finds, which is the OLD global install. Symptom: the artifact check "fails" while the code is fine, or passes while the fix is absent. Reported by the phase-lifecycle session on 2026-08-13 after hitting exactly this while verifying 0.27.0, and it matches how the 0.26.0 smoke test in this repo behaved before the same correction. Fix: `export PATH="<prefix>/bin:$PATH"` for the whole check, and confirm with `sofar --version` inside the scratch repo. Companion fact from the same report: `sofar init` takes no initiative argument.
