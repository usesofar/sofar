# session-driver

Goal: Automate the session handoff sofar already makes content-complete: a stateless driver (sofar drive <initiative>) that runs an initiative task-by-task through fresh agent sessions, records every handoff as events in the record, and reaches any headless agent through a three-call adapter (launch, usage, wait) — Claude Code first, a second adapter to prove the contract. The record is the queue; the driver holds no state of its own.

Standing constraints — obey verbatim (10):
- [D1] sofar may launch the operator's own agent process under the operator's auth, but it never holds API keys, never infers, and never sends user content off the machine; any further guard-rail deviation must be logged as a Decision naming the rail it supersedes before the work proceeds.
- [D2] The driver holds no state outside the record and never implements an agent loop of its own — it launches existing headless agents through the adapter, and every driver-side state change is an event in packages/schema.
- [D3] An adapter never reports record state: wrote_back and the launched session's identity are derived from the fold, and when several candidate sessions exist the driver records a stall rather than guessing.
- [D5] Driver handoff reasons are derived from the fold — needs_user is the named task in status `blocked`, task_done needs a write-back AND a terminal task status; never infer a reason from write-back prose or an exit code.
- [D6] `sofar drive` never creates or destroys a git worktree or switches a branch; it launches into one directory for the whole run and refuses to start unless that directory's `.sofar` log for the initiative is the same file it is driving.
- [D8] A driven session's permission surface is recorded in `run_started.surface` and its settings file is written, read back and compared at EVERY launch — never assert a surface the record does not carry, and never claim the driver bounds what a session can do, since its file only adds to the operator's own settings sources.
- [D9] An adapter declares what it CANNOT do — usage, nudge, permission_rules, cost — and the driver states the consequence on the run's progress stream before the work starts; never let an inert flag (a cost cap that cannot fire, an allow-list the agent cannot express) pass silently into an unattended run.
- [D11] State the driver's token result as a measurement with its scope — 2.44M vs 5.80M per task on the 4.1 run, for tasks that fit one cold session — never as a general claim that driving is cheaper. Where this and D1's rationale disagree, the measurement wins.
